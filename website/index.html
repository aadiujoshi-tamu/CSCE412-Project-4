Meridian Cloud Load Balancer

Meridian Cloud's traffic management engine, written in C++. It distributes incoming web requests across a pool of web servers and automatically adds or removes servers to keep the request queue in a healthy range.

C++ engine Dynamic server scaling IP range firewall Config file driven Verbose / quiet logging Bonus: job-type Switch

1. Overview

Meridian Cloud is a cloud hosting provider that serves web traffic for its customers around the clock. Incoming requests wait in a queue, web servers pull work from it one request at a time, and the load balancer watches the queue to decide whether it needs more or fewer servers.

What the program does

  • Uses configurable simulation settings for server counts, run time, cooldown, random arrivals, request duration, and blocked IP ranges.
  • Fills the queue with servers × 100 random requests, then keeps adding new ones at random times.
  • Screens every new request against an IP range blocker before it is queued.
  • Lets each server process one request at a time for a random number of clock cycles.
  • Keeps the queue between 50 × servers and 80 × servers by adding or removing one server, then waiting n cycles.
  • Writes a color-coded console output and a log file, with a summary at the end.

4. Workflow Flow Chart

The driver sets everything up once, then repeats the same steps for every clock cycle until the requested run time is reached.

decision   side action   process step   (S = current number of servers, T = total run cycles)

Text description of the workflow

  1. Startup. main() loads the configuration file, lets the user override the number of servers and the run time, and picks verbose or quiet mode. It then creates the Logger, the IPBlocker (with the configured ranges) and the LoadBalancer.
  2. Initial load. The LoadBalancer creates N WebServers and fills its RequestQueue with N × 100 randomly generated Requests. This is the “full queue” the load balancer starts from.
  3. Clock loop. While clock < T, the program repeats the following for each cycle:
    1. Finish current work: servers that were busy at cycle start advance one tick; completed requests are recorded and those servers become idle.
    2. Arrivals and firewall: the generator creates this cycle's random batch. Each source address is checked; blocked requests count as rejected and allowed requests enter the FIFO queue.
    3. Scaling: when cooldown permits, compare the post-arrival queue to the thresholds and make at most one server-count change. A server selected for retirement finishes its current request and is removed once idle.
    4. Assignment: idle, non-retiring servers take the oldest queued requests. New assignments do not tick until the next cycle.
    5. Advance: record end-of-cycle queue/server statistics, then advance the clock. At the final cycle, queued and in-flight requests are reported without draining.
  4. Finish. When the clock reaches T, the Logger prints and writes a final summary: requests generated, completed, blocked and still queued; servers added and removed; peak and final server counts; average queue size; and utilization per server.

5. Scaling Policy & IP Blocker

Dynamic server scaling

Let S be the current number of servers and Q the queue size. The goal is to keep Q between 50 × S and 80 × S.

every cycle, after arrivals:
    if cooldown has expired:
        if Q > 80 * S:                 add one server
        else if Q < 50 * S and S > min_servers:
            remove one idle server, if available
            otherwise defer scale-down
        if server count changed: restart cooldown
    assign FIFO work to idle servers

Here Q is the waiting queue and S is the current server count. Comparisons are strict and scale-up is checked first. Cooldown counts cycles after a successful server-count change; an unchanged or deferred check does not restart it. Scale-down removes only an idle server, so active work is never abandoned. The pool respects configurable minimum and maximum server counts. The exact cycle order, request duration contract, counters, and interfaces are recorded in the system design.

IP range blocker (firewall)

The IPBlocker stores each blocked range as a pair of 32-bit integers (low and high). Incoming addresses are converted to integers and compared against every range, so a check is a simple numeric comparison. This gives Meridian Cloud a basic firewall and denial-of-service filter: a burst of requests from one range is dropped before it ever reaches the queue and appears in the log as a blocked event.

Run modes

  • Verbose: logs every change event (server added or removed, request blocked, thresholds crossed), not every clock cycle.
  • Quiet: prints only a starting summary and an ending summary.

Console colors

  • Green: server added / normal progress
  • Yellow: server removed / warnings
  • Red: blocked request / overload
  • Cyan: summaries and headers

Summary contents

Each cycle has a configurable chance of generating an inclusive-size request batch. One configured random seed drives arrival timing, batch size and request details, so the same settings reproduce the same workload. The start summary lists the configuration used. The end summary reports total requests generated, completed, blocked and left in the queue; servers added, removed, peak and final; minimum, maximum and average queue size; and per-server jobs completed and utilization. The required deliverable log is a run of 20 servers for 100,000 clock cycles.

Planned file layout: main.cpp, Request.h, RequestQueue.h/.cpp, WebServer.h/.cpp, IPBlocker.h/.cpp, LoadBalancer.h/.cpp, Config.h/.cpp, Logger.h/.cpp, Switch.h/.cpp (bonus), and a Makefile.

7. Bonus: Switch and Multiple Load Balancers

The Switch sits above two LoadBalancer instances. Each incoming request is inspected for its jobType: streaming jobs (S) go to the streaming LoadBalancer and processing jobs (P) go to the processing LoadBalancer. Each balancer has its own queue, server pool, scaling thresholds and statistics, so the two workloads scale independently. The Switch's stepAll() advances both balancers on the same clock, and report() prints a separate summary for each, which also covers the “multiple load balancers running concurrently” objective.
